# Operator version management with Red Hat Advanced Cluster Management 

[Red Hat Advanced Cluster Management for Kubernetes (RHACM)](https://www.redhat.com/en/technologies/management/advanced-cluster-management) can be used to ease the management of multiple OpenShift and Kubernetes clusters by enabling governance policy and configuration enforcement through a single pane of glass control panel. It's based on the [Open Cluster Management](https://open-cluster-management.io/) upstream project.

Red Hat OpenShift 4 comes with the built in [Operator Lifecycle Manager (OLM v0)](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/operators/administrator-tasks) framework to install Kubernetes Operators from Catalogs. Installing and upgrading operators are simple using the OpenShift Console, but the `Manual` approval process can be cumbersome using GitOps pattern or other automation solutions. RHACM addresses this problem with `OperatorPolicy` policies that can be used to automatically upgrade operators up to certain version. See:

- OperatorPolicy blog: https://developers.redhat.com/articles/2024/08/08/getting-started-operatorpolicy
- OperatorPolicy docs: https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_management_for_kubernetes/2.16/html/governance/governance#operator-policy-ctrl

## How to upgrade to different operator versions in different environments

New versions of operators - just like any software components - should be tested first before allowing an upgrade on a production environment. This can be challenging using the `OperatorPolicy` in RHACM as the `Policy` templating solution only works within a value, but not on the whole yaml scope. See:

- Templating blog: https://www.redhat.com/en/blog/applying-policy-based-governance-at-scale-using-templates
- Templating docs: https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_management_for_kubernetes/2.16/html/governance/governance#template-processing

This repo shows two solutions to address the problem of upgrading to a different operator version based on the environment. These Helm charts share the same structure for `values.yaml`, for example to test _OpenShift Pipelines Operator_ `v1.20` in QA/UAT, meanwhile running `v1.16` in PROD, we can set the values something like this:
```
...
environments:
  - name: qa
    targetVersion: openshift-pipelines-operator-rh.v1.20.5
  - name: uat
    targetVersion: openshift-pipelines-operator-rh.v1.20.5
  - name: prod
    targetVersion: openshift-pipelines-operator-rh.v1.16.4
```

### Repo [operatorpolicy-directly-helm](operatorpolicy-directly-helm)

This Helm chart can be used to create `OperatorPolicy` resources directly on the managed clusters. So these policies are not "pushed" by the hub cluster, but they exist only on the target clusters and show up as _Discovered Policies_ on RHACM UI. This solution is easier to understand and it uses Helm templating only, which makes it simple to reproduce using any automation tools.

### Repo [operatorpolicy-policy-template](operatorpolicy-policy-template) (recommended)

Here we create a standard RHACM `Policy` - with placement and binding - containing an `OperatorPolicy` which is pushed down by the hub cluster to the managed clusters. In the policy we apply templating where certain versions are allowed based on the target clusters' `env` label. These template expressions are generated by a custom Helm helper function, which makes the solution more specific and complex to read.
